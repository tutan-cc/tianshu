## 1. 素材侧：百炼 Qwen-TTS 重做 43 条

### 1.1 端点与模型（三个实测的坑）

| 项 | 值 |
|---|---|
| 接口 | `POST https://{业务空间}.cn-beijing.maas.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation` |
| 模型 | `qwen3-tts-flash`（另有 `qwen3-tts-instruct-flash` 可用，本轮未采用，见 §1.3） |
| 音色 | 共用目录 `Aiden`；`seat1` `Aiden`（原试 Marcus，盲听不合格已换，见 §5.3）、`seat2` `Serena`、`seat3` `Cherry` |
| 请求体 | `{"model":"qwen3-tts-flash","input":{"text":"红中","voice":"Aiden"}}` |
| 后处理 | `python tools/audio/process_sfx.py --src <工作区> --out audio/mj --preset word` |
| 成品规格 | mp3 · 48kHz · 单声道 · 128kbps（与 `audio/` 里其它素材一致） |

三个坑（都实测过，写进 `gen_mj_bailian_tts.py` 的文件头）：

1. **OpenAI 兼容模式没有 `/audio/speech`** —— `POST {base}/audio/speech` 返回 **404**。
   Qwen-TTS 只能走 DashScope 原生 `multimodal-generation`（同一个 host，换路径）。
2. **返回体里是「临时 URL」不是音频字节** —— 必须自己再下载一次落盘（URL 带签名与过期时间）。
3. **下回来的东西扩展名像 mp3、内容其实是 24kHz PCM WAV** —— `ffprobe` 显示 `pcm_s16le`。
   直接当 mp3 用，部分播放器会解码失败，所以**必须**过一遍 `process_sfx.py --preset word`（它顺手转成 48k/128k mp3）。

## 2. 代码侧：`mahjong.js`

### 2.1 念名映射：牌面字符 → 素材词 → 文件

改造前 `VOICE_NAMES` 的键是**牌面字符**（东/南/西/北/中/發/白），文件名直接由键拼出来，
所以「打中念什么」完全由素材文件名决定 —— 想改念法就得改代码语义。现在拆成两张表：

```js
var VOICE_HONOR_WORDS = { 东:"东风", 南:"南风", 西:"西风", 北:"北风", 中:"红中", 發:"发财", 白:"白板" };
var VOICE_NAMES       = { 一万…九筒(27) + 东风…白板(7) + 碰/杠/…/流局(9) };   // 键 = 素材文件基名
function voiceFile(name) {
  var s = ...;
  if (VOICE_HONOR_WORDS[s]) s = VOICE_HONOR_WORDS[s];   // 牌面字符先换成念法
  return VOICE_NAMES[s] ? (s + ".mp3") : "";
}
```

四处顺手修掉的隐患：

1. **`voicePreload()` 原来直接拼 `k + ".mp3"`** —— 字牌改名后它会去请求 `东.mp3`/`中.mp3` 这种已经不存在的文件
   （每个座位 4 次 404，而 `AudioSys` 不会因为一次失败请求报错，测试也测不出来）。现在统一走 `voiceFile()`。
2. **删掉了「看到首字就返回」的旧写法** `if (s.charCodeAt(0) === 0x767C) return "发.mp3";` ——
   它会把「發财」也截成「发.mp3」，而且**绕过 `VOICE_NAMES`**：词表里有没有这条都不再被检查。
3. 素材词表与素材文件现在是**同一个键**，`voiceUrl("东风")` 与 `voiceUrl("东")` 都通 —— e2e 层可以直接拿文件名来问。
4. `VOICE_CALLS` 白名单里保留了用户点名的「暗杠/补杠」两个词（它们**不喊牌**、出牌碰实音，不在素材里），
   登记它们只是为了标明「这类动作属于高优先级」。

### 2.2 播报队列（本次的核心改动）

改造前（原注释就写着）：

```js
/* 播一条喊话：同一时刻只播一条（后一条打断前一条） */
if (VOICE_CUR) { VOICE_CUR.pause(); VOICE_CUR.currentTime = 0; }
```

现在的三条规则：

| # | 规则 | 实现 |
|---|---|---|
| ① | **串行**：同一时刻只播一条，只有它 `ended`（或出错/超时兜底）才轮到下一条 | `voicePump()` + `voiceStart()` 的 `finish()` |
| ② | **优先级只决定排队顺序**：喊话插到报牌前面；同优先级一律 FIFO | `voicePush()` 找「第一个优先级更低的项」插进去 |
| ③ | **绝不抢占正在播的那条** | `voiceStart()` 里没有任何 `pause()`；这就是「出牌不打断喊话」的硬保证 |

参数与兜底：

| 机制 | 取值 | 理由 |
|---|---|---|
| 优先级 | 喊话 `2` > 报牌 `1` | 碰/杠/暗杠/补杠/杠开/抢杠/胡/自摸/流局 算喊话 |
| 队列上限 | **6** | 四家连打时队列会越排越长，喊话要等五六秒才响，听起来对不上牌局 |
| 队满策略 | 丢**最旧的低优先级**项；若新来的比队列里所有项都低，**丢它自己** | 绝不为了报一张牌把已排队的「碰/杠/胡」挤掉 |
| 最小间隔 | **120ms** | 与该条自带的 `delay`（AI 出牌 170ms）取较大者 |
| 卡死兜底 | `duration*1000 + 1500ms` 看门狗 | `ended` 不来（解码失败/宿主挂起）也要让队列继续走 —— 队列卡死比少播一条严重得多 |
| 清理时机 | 关语音开关 / `dispose()` / 重新开局 | `voiceStopAll()`：清队列 + 停播 |

### 2.3 新断言抓出来的一个真 bug（值得单独记）

写完队列、跑新断言，第一条就红了：**连说三条，只有最后一条能响，前两条凭空消失**。

根因：`voicePump()` 把条目从队列摘出后要等 `VOICE_GAP` 才 `voiceStart()`，
这段窗口里 `VOICE_PLAYING` 还是 `null`；下一次 `say()` 进来又走一遍 `voicePump()`，
它 `clearTimeout` 掉上一个定时器 → 上一条被静默丢掉。
**而且 `plays` 计数、队列长度看起来全都正常** —— 不写时序断言根本抓不到。

修法：`voicePump()` 一取到条目就**立刻占住播放位**（`VOICE_PLAYING = it`），
`voiceStart()` 改成「不是当前占位者就直接退出」，取消由 `voiceStopAll()` 负责。

### 3.2 同一文件：词表映射的「首字替换」写法

原代码把素材文件名当「代码词汇」来猜：

```js
return n.charAt(0) === "\u53d1" ? "\u767c" + n.slice(1) : n;   // 发 → 發
```

改名后它会造出 `發财` 这种不存在的名字（误报）。现在**素材文件名就是词表的键**，直接交给 `voiceUrl()`；
牌面字符（东/發/白…）→ 念法的映射由 `tools/test/mahjong-logic.js` 单测覆盖。

### 3.3 同一文件：固定 Chrome profile 的磁盘缓存 —— 差点让验收测的是**旧代码**

第一次跑「改后」的接线核对，素材侧全绿（251 个文件 HTTP 200），却报：

```
✗ 四个座位所有牌名 URL 均可取到  [144/172 坏:空URL seat0/东风 | 空URL seat0/白板 | …]
```

结果发现**浏览器里跑的还是缓存里的旧 `mahjong.js`**（旧词表里没有「东风」这个键）——
脚本用的是固定 profile（仓库里的 `_prof_wiring`），缓存跨次运行留着。
换一个全新 profile 立刻正常（同一份代码、同一个服务器）。
已加 `--disk-cache-size=1 --media-cache-size=1` 关掉磁盘缓存；
**加了之后连旧的脏 profile 都不用清就已经 10/10**（本条是验证过的，不是推测）。

> 这条比测试失败更危险：**断言测的不是你改的那份代码**。任何用固定 profile 的 e2e 都该关缓存。

## 5. omni 听觉验收（`qwen3.8-omni-flash`）

### 5.1 方法（为什么不能直接问「念得对吗」）

| 设计 | 原因 |
|---|---|
| **盲听**：提示词只要求「逐字写出你听到的中文」，**不提期望答案**，并明确给出「若几乎听不到人声就回答：无」这个出口 | `omni_judge.py` 实测过：提示词若预设「里面一定有内容」，模型会对纯静音编出「确认蜂鸣声」 |
| **拼音同音匹配**当判据（`pypinyin`，无调） | `九筒↔酒桶`、`碰↔砰` 完全同音，拿汉字串比会把正确件判错（第一版探针就误报了 17 条） |
| 每条 **2~3 遍**，任一遍同音即通过 | 短促喊牌识别率天然低；`verify_mj_asr.py` 的结论是「单条判错不可信」 |
| 判错 → **重生成**（TTS 是随机采样）→ 重听 | 用户要求的循环；实测同一个词不同采样的识别结果差别很大 |

### 5.4 这道验收的边界（必须说清楚）

* **它证明的是「念得能被听出来」，不是「音频一定标准」**。`0.25~0.6s` 的单音节短词
  （碰/杠/胡/过/听）是模型的重灾区，实测它在同一批文件上会蹦出**日语、韩语、俄语、阿拉伯语**，
  还有 `3万→One`、`自摸→Zoom out` 这种明显是猜的输出 —— 这些**不代表音频里真的念错了**。
* 反过来说，`八筒→马桶` 这种两遍都一致的偏差就值得查（本次已重做）。
* **静音/削波/时长这类「物理是否合格」不能交给模型** —— 那是 `check_audio.py` 的活，
  本次两层都跑了：声学 43 条全过，听觉按上表。
