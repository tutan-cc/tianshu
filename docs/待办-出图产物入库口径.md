# 待办：出图产物该不该入库（`_shots/`、`*.png`）

> 发现于「拉取 v1.33 + 卡牌对决后逐个跑新增工具」这一轮。**不是 bug**，是一处口径不统一，交给作者定。

## 现象

仓库根和 `_shots/` 下有一批 PNG，**是脚本可再生成的产物，却被 git 跟踪**：

| 文件 | 生成脚本 |
|---|---|
| `_sfx-preview.png` | `tools/dev/sfx-check.js` |
| `_shots/0*.png`（7 张） | `tools/dev/cardfight-shot.js` |
| `card-preview.png` | `tools/dev/card-preview.js` |
| `palette-check.png` | `tools/dev/palette-check.js` |
| `sprite-sheet.png` | `tools/dev/sprite-sheet.js` |
| `_cabinet-frame.png` | 打斗 2.0 定稿帧 |

它们由 `cd86067` / `470e9d2` 等提交引入并跟踪。

## 为什么值得讨论

`.gitignore` 里已经有两条「出图产物不入库」的规则：

```
# 出图流水线的 PNG 产物：由脚本重新生成，不入库（与 dist/test-results/ 同理）
测试截图/
dist/**/*.png
```

但这两条**都不覆盖仓库根与 `_shots/`**，所以那批 PNG 一直是跟踪状态。
结果是：**每跑一次出图工具，`git status` 就多出若干改动**，容易混进无关提交。

本轮就出现了这个情况 —— 我为了验证 4 处硬编码路径修复而重跑出图工具，
`_sfx-preview.png` 与 `_shots/*.png` 全部变成 modified，跟着一起提交了（`36f3da9`）。
按同事自己的做法（他当年也是连图带脚本提交）不算错，但口径不一致：
同样是出图产物，`测试截图/` 忽略、`_shots/` 跟踪。

## 两个选项

**A. 保持跟踪**（现状）
- 好处：这些图是**给人看的设计参考**，clone 下来直接能看，不必先跑工具；
  对协作者友好（尤其 `_cabinet-frame.png` 是定稿帧，有留存价值）。
- 代价：每次跑出图工具都会产生 diff，得记得别把它们混进功能提交。

**B. 改为忽略**（与 `测试截图/` 一致）
- 好处：`git status` 干净，出图工具随便跑。
- 代价：clone 后看不到那些参考图；需要某张图时得先跑对应脚本（部分依赖浏览器/Chrome）。

## 建议

**倾向 A（保持跟踪），但把口径写清楚**，避免以后又有人问「为什么这个 png 入库那个不入库」：

- `_shots/`、根目录 `*.png` = **设计参考图，入库**（人看的）
- `测试截图/`、`dist/**/*.png` = **测试/出图流水线产物，不入库**（脚本看的）

若采纳，建议在 `tools/README.md` 的「生成物落 dist/」那节补一张表说明这个分界。
若你更想要干净 `git status`，那就把 `_shots/` 与根目录那几个 png 加进 `.gitignore`
并 `git rm --cached`（历史仍保留，不会丢）。
